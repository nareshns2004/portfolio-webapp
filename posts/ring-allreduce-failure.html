One dead link, 512 idle GPUs: ring all-reduce under failure

Ring all-reduce is close to bandwidth-optimal, and that same design makes it a chain. Break one link and every rank stalls, then every rank reports the same timeout.

Naresh Kumar · Oct 2026 · 8 min read

TL;DR
  • Each GPU in a ring all-reduce sends about 2·S bytes no matter how many GPUs there are. That is why rings scale.
  • Every step depends on the neighbour’s previous step, so one failed link stalls the whole ring within N−1 steps.
  • Every rank then times out in the same collective with the same message. The first rank to report it is usually not the culprit. Symptoms are global, causes are local.

Why a ring?

Data-parallel training ends every step by summing gradients across all GPUs. The naive approach sends everything to one GPU and broadcasts the result back, which makes that GPU’s link the bottleneck. Ring all-reduce arranges the N GPUs in a cycle and splits the buffer of size S into N chunks:

  1. Reduce-scatter (N−1 steps): each GPU sends one chunk to its right neighbour and adds the chunk arriving from its left. Afterwards, each GPU owns one fully-reduced chunk.
  2. All-gather (N−1 steps): the reduced chunks travel once more around the ring until every GPU has all of them.

Each step moves S/N bytes per link, and there are 2(N−1) steps. The standard α-β cost model gives:

T(N, S) ≈ 2(N−1)·α + 2·(N−1)/N · S / B

Here α is per-step latency and B is per-GPU link bandwidth. The bandwidth term approaches 2S/B as N grows, so it is independent of cluster size. The latency term grows linearly with N, which is why NCCL also has tree and other algorithms for small messages at scale. Try it:

The price of being a chain

Nothing in the ring is optional. In step s, a GPU can only send what it finished in step s−1, and it can only finish step s−1 once its left neighbour’s data has arrived. Every rank depends on every other rank within one lap.

Run the ring below, then click any link to cut it mid-collective (or use the button). The stall spreads one hop per step until every rank is waiting. Then the watchdogs fire.

What every rank sees

Look at the log after the watchdogs fire. Every rank reports the same thing: a timeout in the same ALLREDUCE, with the same sequence number. The order is effectively random, because each rank’s watchdog thread wakes on its own schedule. The rank that reports first is just the one whose timer ran out first.

This is the core attribution problem in multi-node training. One bad cable produces N identical error messages, and the most visible one (the first in the aggregated logs) points at the wrong machine. Real clusters make it worse:

  • Detection is slow. The default timeout for a PyTorch NCCL process group is 10 minutes, so a cluster sits idle for minutes before anything fires.
  • Many causes look the same. A dead link, a GPU that fell off the bus, a hung kernel on one rank, and a congested fabric that slows one hop all end as a collective timeout.
  • Real NCCL is more tangled than one ring. It runs multiple channels, rings and trees across NVLink and the network, so a single failure can stall several of them at once.

What attribution actually needs

To name the culprit, you need evidence that differs across ranks, not the error message that is identical on all of them:

  • Per-rank collective progress. PyTorch’s NCCL flight recorder keeps a ring buffer of recent collectives per rank. Comparing the last completed sequence number across ranks shows where the chain broke: the ranks that were stuck earliest sit right after the break.
  • Lower-layer telemetry in the same time window: GPU Xid events and DCGM health, NIC error and pause counters, link flaps from the switch.
  • Topology to map “rank 3 waiting on rank 2” onto a physical NIC, cable and switch port.

The simulator’s step counters stand in for that flight recorder. Cut a link, let it run, and compare the step numbers: the lowest one sits just downstream of the cut. Try the incident drill to do the same with mixed signals.

Why it matters for recovery

Without attribution, the only safe move is to restart the whole job from the last checkpoint. Every rank pays for process start, CUDA and NCCL init, checkpoint load and warmup, plus the work since the last checkpoint, and the job may land on the same bad link again. With attribution, smaller recoveries become safe: drain one node, re-initialize communicators, and restore from a peer’s in-memory copy. How often you should checkpoint depends on all of this; there’s a calculator for that.

This is what I’m building in goodput: fault injection with ground truth, flight-recorder signature capture, cross-layer correlation, and topology-aware recovery. It’s at milestone 1 of 6, with the design and harness in public and no results yet.

Model & assumptions

  • The cost model is the textbook α-β model for one ring. It ignores pipelining, multiple channels, NVLink vs network hierarchy, protocol choice (LL/LL128/Simple) and reduction compute.
  • busbw = algbw · 2(N−1)/N, following the nccl-tests convention, so results are comparable across N.
  • The simulator runs one ring, one chunk per step, and a fixed watchdog compressed to a few seconds. The log lines are modeled on PyTorch’s ProcessGroupNCCL watchdog message. They are illustrative, not captured from a cluster.
